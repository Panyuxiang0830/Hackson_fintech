# 四类审计工作台方案

2026-10-16；REQ-006/audit_console_four_domains、REQ-008。authority=team_decision，status=in_progress。2026-10-16用户已确认本方案，进入实现与部署验收。

## 已确认的目标

用户将审计分为获取信息、权限变更、资料更新、越权事件四部分；前两部分是主要内容，后两部分正常情况下收起，点击摘要框后才展开。页面最上方提供统一AI审计提问入口，每部分也可以独立查询。管理员完整查看已记录的审计内容，不再受其当前业务文档读取权限遮蔽。

本方案不改变普通员工的业务权限。管理员看到的是日志已有的历史问题、回答、资料标识/版本和变更记录；没有存进旧日志的资料正文、标题快照或修改前后值，不承诺能从历史记录还原。

## 已有AI功能核实

- POST `/api/audit/ask` 调用 UnifiedService.audit_query(generate=True)，由 AuditAnswerer 解读查询结果，校验[E序号]事件引用并把审计问答本身写入日志。
- 线上历史事件E98记录provider=openai_compatible/glm-5.3-flash、decision=answered、attempts=1，说明有真实模型调用成功记录。
- 当前Stitch页面仅接GET `/api/audit`，没有调用该AI接口。现有模型输入最多20条事件且缺少完整权限变更/资料更新字段；不能直接宣称已支持完整四域分析。
- 上述为方案阶段核实；用户确认后已实施管理员完整审计和四区工作台，真实模型与服务器验收结果见文末。

## 页面布局

```text
┌────────────────────────────────────────────────────┐
│ Ask audit AI                                       │
│ 输入自然语言问题                 [时间范围] [Ask]  │
│ 回答 / 使用的筛选条件 / 可点击事件引用              │
├─────────────────────────┬──────────────────────────┤
│ 获取信息                │ 权限变更                 │
│ 默认展开，独立筛选      │ 默认展开，独立筛选       │
│ 事件列表、分页、详情    │ 变更列表、分页、详情     │
├─────────────────────────┼──────────────────────────┤
│ ▸ 资料更新 · N条        │ ▸ 越权事件 · N条         │
│ 最近更新 / 结果摘要     │ 最近事件 / 状态摘要      │
└─────────────────────────┴──────────────────────────┘
```

桌面端两列，窄屏按上述顺序竖排。后两卡片展开后显示各自的搜索条件、列表和分页；收起时保留摘要。AI输入不隐藏四卡片；回答中的事件引用会定位到相应区域、展开并打开该事件详情。

页面主要入口是自然人名、资料名/ID、来源和项目；请求ID、原始JSON、哈希链验证作为详情/高级工具保留。四个区域首次加载已有事件，零条显示明确空状态，避免初始0 found被误认为日志为空。

## 四个区域

| 区域 | 主列表内容 | 独立筛选与详情 |
| --- | --- | --- |
| 获取信息 | 时间、员工、动作、问题或资料摘要、结果 | 员工、搜索/提问/打开原文、来源/资料、关键词、时间；展开查看原问题、记录回答、返回/使用证据、文档版本和授权记录 |
| 权限变更 | 时间、操作者、目标员工、权限对象、前→后、执行结果 | 操作者和受影响员工分别可选，来源/项目/密级/部门/账号类型、时间；详情保留范围、操作ID、目标权限版本及处理阶段 |
| 资料更新 | 收起时显示数量、最近更新时间、发布/失败摘要 | 展开后按来源、资料、操作人、任务状态、时间查询，展示任务ID及旧/新版本；不能仅凭新版本推断修改内容 |
| 越权事件 | 收起时显示数量、最近事件、被阻断状态 | 展开后看操作者、接口/操作、请求目标、已记录的拒绝原因、时间和风险级别 |

获取信息中将search、answer、document_open分开，不能把检索候选当成员工已经主动打开原文，也不宣称已证明人实际阅读。普通无结果提问不属于越权；仅有404无法区分资料不存在和无权，不能直接定为严重违规。明确的未授权管理接口访问、无效认证、凭据异常等归入越权/异常，并注明是被阻断的尝试。

默认查看最近24小时，可切换全部或自定义范围。日期显示SGT，查询范围转换为带时区的UTC后存储/执行；自然语言“今天”采用同一SGT口径，界面显示实际起止时间。各卡片有自己的条件，AI回答另显示它采用的条件，不静默改掉四区已有筛选。

数量由数据库按当前范围统计，列表使用稳定游标分页；不把最多100条返回列表长度标成全时段总数。

## AI入口

用户可以跨四类提问，例如：

- 今天Jax查过什么、打开过哪些资料？
- 谁撤销过Jax的Slack权限，之后他还能访问吗？
- SwiftUI项目最近有哪些成员权限变化？
- 今天哪些资料更新发布失败了？
- 最近有没有人尝试访问没有权限的管理接口？
- 对照今天的权限变更和访问记录，解释发生了什么。

处理链：自然语言识别对象/动作/范围 → 显示实际查询条件 → 后端执行受限查询与必要聚合 → AI基于结果解释 → [E序号]链接到原始审计事件。

复用现有AuditAnswerer及LLM_AUDIT配置，补充四类结构化输入和受限查询规划；普通具体问题优先确定性解析，跨类问题使用受约束的查询计划，不允许生成任意SQL。模型不决定记录是否存在、是否构成已证实违规或统计数量。计数、分组、时间顺序由后端计算；只读取部分明细时明确覆盖范围。

AI失败时保留已经查出的事件和条件，提供重试。AI回复只读，不执行恢复/撤销权限等管理操作。四区都能问，不表示能回答日志未记录的信息；缺失前后值或历史正文时说明未记录。

## 后端需要一起补的部分

1. 管理员审计读取与业务证据可见性解绑，页面、JSON导出、AI采用一致的完整审计事件视图。旧业务原文是否仍存在，不影响其已记录历史事件显示。普通员工仍不能调用管理员审计接口；其他角色保留现有规则。
2. 统一actor、target_user、resource、action、result、timestamp、operation_id等字段。记录事件发生时的必要名称/对象快照，显示时同时保留稳定ID。
3. 权限变更保存before/after，包括来源开关、项目资格、clearance、department、账号/绑定状态和目标权限版本。意图/完成/失败通过operation_id关联；主列表避免一项操作被重复算成两次变更，未完成意图展示待确认。
4. 新原文失败事件保存请求目标及确知的原因；资料更新事件带任务、范围、版本和发布结果，支持四类查询及AI解释。
5. 增加category、actor、target、keyword、source/project、document、result、start/end查询；修复目前Keywords没有普通全文过滤、按员工漏掉管理员对其变更等问题。
6. 旧事件按类型映射到四区，保持原哈希链不变。旧日志缺失的字段显示未记录，既有记录不伪造回填。演示身份切换、审计查询自身等系统事件保留在高级系统事件中，默认不挤占四类主要记录。

## 验收与边界

- 管理员能看到已记录历史问题/回答/资料ID和具体权限对象，撤权后仍可审计这些历史记录；员工不能访问审计。
- 检索、提问、打开原文、来源/项目/密级变更、发布更新、明确越权拒绝都在正确卡片中可查。
- 按受影响员工筛选可以查到管理员对他的操作；关键词、时间、动作和分页真实生效。
- 顶部AI至少完成一次每类问题、一次跨类问题；数量与后端查询一致，每个事实引用能打开对应日志。
- 两个主要区域默认展开、另外两区默认收起，独立筛选与引用跳转不互相覆盖。
- 测试涵盖新增before/after、旧日志兼容、管理员完整审计、员工拒绝、链完整性、查询/分页、AI事件字段和引用、模型失败回退及浏览器布局；完成后做实际服务器四类与真实模型验证。

本轮范围是上述审计工作台和必要后端补齐；不重构业务知识问答或重建语料索引。
