# 问题理解与检索计划（工作分支已接入）

日期：2026-10-11。关联 REQ-015、REQ-019、REQ-018。Query Planner 已在工作分支接入 search/ask，真实模型收益仍待评测，需求扩展保持 in_progress。具体配置、固定上限和安全测试见 [模型链路实施说明](llm-workflows.md)。不是仅修改回答 Prompt；服务器尚未更新。

问题拆解归入既有 REQ-015，不新增重复需求。规划位于第一次证据检索之前，只读取原问题；页面开关用于基线对照。每次最多一次规划，不对每个子问题递归调用模型。

## 建议流程

服务端解析当前身份 → 保留原问题 → 启用时一次模型规划／关闭或失败时原问题检索 → 校验计划 → 原问题与少量扩展检索 → 各分支执行相同授权过滤 → 去重融合 Top-K → 用原问题和授权证据生成回答 → 单独调用引用复核 → 交付检查。复核默认沿用 GLM；失败或无可用配置不能标为通过，同模型复核不是独立验证。

- 规划输出分别用于不同检索路径：子问题拆开复杂询问，关键词进入 FTS，语义检索句进入 Qdrant；原问题检索和各子问题结果去重融合，不让回答模型直接逐段照抄检索片段。
- 2026-10-11 用户希望提问先过 LLM：启用本功能时，在首次业务证据检索前调用一次规划模型，输出子问题与关键词；关闭时保留原问题/规则检索用于基线对比。已知无业务读取范围时可以直接安全终止；规划失败或超时回退原问题。后续是否按任务启用由收益评测决定，不把旧版按需建议写成当前已接入的行为。
- 子问题/语义检索句分别进入 Qdrant，关键词进入 FTS；两路分别取受限 Top-K，再与原问题结果去重融合为最终 Top-K。Top-K 表示取回数量，不是与关键词或向量并列的另一种索引。
- 规划模型只接收原问题及必要的已授权范围提示，不能预读全库标题或权限库。模型给出的是检索候选，不是业务事实、权限决定或用户已经确认的“话外意思”。
- 首版建议最多 3 个子问题、3 条语义改写、8 个关键词、2 个解释候选，校验长度、枚举、数组与总检索／调用预算；这些上限不是相互相乘的许可，不对每个子问题递归调用规划模型；保留原问题检索。不能把模型输出直接当 SQL、Qdrant filter、user_id 或 principal，来源／项目提示只能与授权范围取交集。
- 口语整理不得删除否定、时间、实体或比较条件。实体纠错需核对当前授权资料的名称候选，多义或改变问题含义时要求用户确认；不能静默把 TibanDB 改为 TitanDB 或 TiDB。
- 规划超时、格式不符或预算耗尽，回退原问题检索而非放开过滤。规划前解析身份，每个检索分支和交付前继续复核当前权限。

## 受限 JSON 示例

下面是字段模板，不是某次真实模型输出；现有实现不要求模型给出 intent，意图仍体现在原问题与子问题中。

```json
{
  "original_query": "TitanDB 是做什么的",
  "sub_questions": [],
  "keywords": ["TitanDB"],
  "semantic_queries": [
    "What is TitanDB and what is its purpose?",
    "TitanDB responsibilities and application use cases"
  ],
  "entity_candidates": [],
  "possible_interpretations": [],
  "needs_clarification": false
}
```

只请求有限候选和澄清信号，不要求或保存完整思维过程。模型回传的 original_query 必须与服务端保存的输入一致，不能覆盖原问题。

复杂问题例如“TitanDB 做什么，哪些服务在用，最近为什么要拆分？”可拆成三个子问题，再分别生成有限的关键词或语义检索句。拆解不会预先认定“已经决定拆分”为事实；最终回答仍须根据实际授权证据回答原问题，无依据的部分说明不知道。

## 启用与验收

- 固定样例覆盖中英口语、多子问题、纠错、否定、时间、不同权限用户、规划失败与规划期间撤权。
- 对比不开启／开启规划的证据召回、无关扩展比例、回答依据、额外延迟及 Token。生成更多关键词不代表更好；当前只通过合成控制流回归，真实收益尚未测。
- 审计保留原问题、策略／模型／Prompt 版本、受限计划元数据及检索分支数量，遵守现有内容脱敏；不重新加入数据摄取审计模块。完整日志策略仍沿用已确认专题。
